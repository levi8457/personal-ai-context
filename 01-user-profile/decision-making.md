# 决策框架

## 1. 权重排序 ![HIGH]
![HIGH] 实测权重：**能立刻看到效果 ≳ 可回滚 ≳ 工程质量**。速度不是"越糙越好"，而是"别让我等，也别让我返工"。

**识别依据**
1. 「a 和 b 我都嫌弃麻烦，我选 c」——三个方案里选操作步骤最少的。
2. 「确认，先实现阶段一，记得更新站点的更新记录」——先要看得见的第一阶段，且要求留痕。
3. 「我经常开发一个项目弄到测试阶段发现很多问题，然后改问题，然后总是改的面目全非的，越改问题越多」——被"无边界重构"伤过，因此重视小步可验证。

**应用示例**
- 方案对比时直接标出「几步操作 / 要不要重启 / 能不能回滚」，不要只讲技术优劣。
- 每次改动都留一条可回滚路径（git 提交、备份文件、compose 回滚命令）。

## 2. 风险偏好：敢授权，但破坏性动作要确认 ![HIGH]
![HIGH] 用户会给到 root/全权（「我允许你往 <服务器> 执行任何命令」「全给你权限」），但对**不可恢复的删除**会单独点头（「确认删除」）。

**应用示例**
```text
常规改动（改代码、重启容器、写文件）→ 直接做，事后汇报
破坏性动作（rm -rf、drop table、卸载软件、覆盖线上数据）→ 先一句话说明影响 + 等"确认"
```

- ✅ 「要删的是 `/opt/old-build`（3.2G，最后修改 2025-12），确认后我执行 `rm -rf`。」
- ❌ 直接执行删除后再汇报。

## 3. 技术选型考量 ![MEDIUM]
![MEDIUM] 偏好**成熟、能立刻验证、运维成本低**的方案；对新奇工具的兴趣停留在"能不能让我少干活/更好看"。

**识别依据**
1. 「cli 工具里外观比较好看的 同时能管理多任务的工具给我推荐一个」→ 接受推荐并安装（zellij），但出问题要求彻底卸载。
2. 模型选择：因"慢"从 Atria 换 Agents-A1，又接入 DeepSeek / Nous 免费模型——**性价比与响应速度优先于最强推理**。
3. 站点问题：要求「不走 8888 端口」「静态页面路径不要用中文，统一用拼音」——选型直接服务于"别人能打开"。

**应用示例**
- 推荐新技术时，先给「能解决你哪个具体痛点 + 装它要多少磁盘/依赖 + 怎么干净卸载」。
- 涉及公网可访问性，默认选 80/443 或已备案端口，URL 用拼音 slug，不用中文路径。

## 4. 面对复杂问题的分解方式 ![HIGH]
![HIGH] 用户自己的分解习惯是**按可交付阶段**切（阶段一/二/三），并要求每个阶段有可观察产物（页面、更新日志）。

**识别依据**
1. 「读取这个文档根据你的理解确认都能完成后去开发，不确定的可以先跟我提问」
2. 「确认，先实现阶段一，记得更新站点的更新记录」

**应用示例**
```
阶段一（今天）：/changelog 页面 + 一条真实记录 → 你能点开看到
阶段二（明天）：?category=projects 有数据 → 分类页不再空白
阶段三：SEO/结构化数据收尾
每阶段结束我会给：页面 URL + 一条可复现的验证命令
```

## 5. 决策时最讨厌的三种行为 ![HIGH]
1. **反复确认已知信息** → 见 [`communication-style.md`](../06-preferences/communication-style.md#3-反馈与纠错)。
2. **只给结论不给证据** → 他会亲自去线上核对。
3. **把选择权全部推回给他** → 需要的是「推荐 + 一句理由 + 回 1/2/3」，不是开放式提问。

# 贡献指南

> **Agentic Contribution Protocol**
>
> 这份文档指导 Agent 如何从协作历史中提取模式，并为「个人 AI 协作上下文仓库」做出贡献。

## 🎯 角色定义

**你现在是一位「协作模式分析师」**，目标是：
1. 从与用户的协作历史中识别关键模式
2. 将这些模式标准化到仓库对应文件中
3. 持续优化协作效率和用户体验

## 🔄 标准贡献流程

### 阶段 1: 模式识别

#### 1.1 回顾协作历史
分析我们与用户的所有交互记录，关注以下维度：

**沟通与交互模式**
- 信息呈现的偏好（详细 vs 简洁）
- 复杂概念的解释方式（类比、示例、分步）
- 反馈接收偏好（即时 vs 总结）
- 犯错时的处理风格

**技术工作流**
- 代码审查关注点
- 错误调试的层次方法
- 工具使用偏好
- 测试策略偏好

**问题解决框架**
- 复杂问题的分解方式
- 决策权重分配
- 技术选型因素
- 风险偏好程度

**会话管理**
- 会话启动必要信息
- 进度汇报频率
- 任务验收标准
- 中断处理方式

#### 1.2 识别模式等级

**HIGH - 影响用户体验的核心模式**
- 沟通风格的根本偏好
- 关键的技术约束
- 重要的工作习惯

**MEDIUM - 优化体验的辅助模式**
- 工具配置的微调
- 汇报格式的细节
- 代码注释的偏好

**LOW - 锦上添花的细微模式**
- 特定命令的使用习惯
- 输出样式的偏好
- 文档格式的细节

### 阶段 2: 内容生成

#### 2.1 使用标准模板

**模板 1: `01-user-profile/communication-style.md`**

```markdown
## 沟通偏好

### 信息呈现方式
![{PRIORITY}] 用户偏好「简要解释原理，避免冗长背景」

#### ✅ 推荐做法
- 「这个函数的作用是...」直接说明
- 提供最小可运行示例
- 关键部分用 `// 注意：` 标注

#### ❌ 避免做法
- 过多理论背景铺垫
- 过于简化的伪代码
- 不完整的依赖说明

### 反馈接收偏好
![{PRIORITY}] 希望获得：
1. 问题根因分析
2. 3 个可能的解决方向
3. 推荐优先级和理由
```

**模板 2: `02-technical-stack/code-conventions.md`**

```markdown
## 代码规范

### 命名约定
![{PRIORITY}] 
- 函数：`camelCase`，动词开头，如 `calculateTotal()`
- 常量：`UPPER_SNAKE_CASE`
- 类名：`PascalCase`

### 错误处理
![{PRIORITY}]
- 显式错误检查
- 提供有意义的错误信息
- 避免捕获过于宽泛的异常
```

**模板 3: `03-collaboration-patterns/task-breakdown.md`**

```markdown
## 任务分解偏好

### 复杂任务处理
![{PRIORITY}] 期望按以下步骤：

1. **理解阶段**：确认核心需求，识别约束
2. **方案阶段**：提供 2-3 种实现方案
3. **执行阶段**：分步实现，主动汇报进度
4. **验证阶段**：自检并说明测试方法
5. **总结阶段**：回顾和优化建议
```

### 阶段 3: 安全检查

#### 3.1 隐私保护清单
- [ ] 不包含真实 API 密钥或密码

#### 3.2 准确性检查
- [ ] 技术栈版本信息准确
- [ ] 代码示例可实际运行
- [ ] 描述符合实际情况
- [ ] 优先级标注合理

#### 3.3 实用性验证
- [ ] 内容能让新的 Agent 直接应用
- [ ] 包含具体的示例和场景
- [ ] 描述了边界条件和例外情况
- [ ] 提供了实际操作的价值

## 🔍 模式识别技巧

### 1. 高频模式识别
如果某个操作、命令或偏好出现 3 次以上，很可能是一个重要习惯。

### 2. 情绪标记识别
当用户明显表现满意或不满意时，通常对应重要的偏好。

```
用户显式满意："这个很好，请保持"
用户显式不满："这个方式效率太低"
```

### 3. 重复询问模式
如果用户反复询问同类问题，可能是信息缺失或沟通不畅。

### 4. 问题解决的框架识别
用户如何解决不同类型的问题，可以总结出通用的方法论。

## 📊 贡献质量评估

### 评估维度
- **准确性**：是否真实反映用户偏好？（1-5 分）
- **实用性**：新 Agent 能否直接应用？（1-5 分）
- **完整性**：是否包含足够的上下文？（1-5 分）
- **时效性**：是否及时更新？（1-5 分）

### 评估标准

**卓越 (5 星)**
- 基于多个具体案例
- 包含正面和反面示例
- 优先级标注清晰
- 内容可直接使用

**良好 (4 星)**
- 基于 2-3 个案例
- 包含示例说明
- 优先级合理
- 需要少量调整即可使用

**合格 (3 星)**
- 基于 1-2 个案例
- 有基本描述
- 优先级不明显
- 需要进一步澄清

**需改进 (1-2 星)**
- 案例模糊或不完整
- 描述过于抽象
- 缺少具体示例
- 难以直接应用

## 🎯 高级功能：模式预测

### 识别潜在需求
基于用户对特定任务的反应，预测可能需要的模式：

```
如果用户：
- 总是问"还有其他方法吗？"
→ 则识别出：偏好多方案对比

如果用户：
- 频繁询问"为什么这样实现？"
→ 则识别出：重视技术原理理解

如果用户：
- 总是关注"性能如何？"
→ 则识别出：性能优先的决策框架
```

### 动态优先级调整
基于模式的重要程度和使用频率，动态调整优先级：

```
初始发现：MEDIUM
使用 5 次以上 + 用户正面反馈 → HIGH
跳过 3 次以上 + 无反馈 → LOW
```

## 🔄 持续优化

### 季度审查
每季度进行一轮全面模式识别：
- 更新技术栈信息
- 确认偏好是否变化
- 清理过时内容
- 添加新发现的模式

### 版本控制
- 主分支：`main`（稳定版本）
- 开发分支：`dev`（测试更新）
- 功能分支：`feature/贡献-模块名`

### 向用户反馈
在贡献完成后，向用户发送总结：

```
我注意到一些协作模式，已更新到上下文仓库：

✅ 新增模式：
- [HIGH] 偏好提供多种实现方案对比
- [MEDIUM] 代码注释风格：需要详细注释

📝 需要您确认：
- 这些模式是否符合实际？
- 优先级标注是否准确？
- 是否有遗漏的重要信息？

请审核并确认，如有需要我继续调整。
```
